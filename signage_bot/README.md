# Telegram-бот для согласования вывесок — пилот

Бот Центра урбанистики Астаны. Консультирует предпринимателей по типовым
вопросам согласования вывесок строго на основе утверждённой базы знаний
(19 содержательных ответов + служебные тексты). При любой неуверенности —
не отвечает, а передаёт диалог живому оператору в панель. Любое фото/эскиз
всегда уходит оператору. Всё логируется в Google Sheets, фото — в Google Drive.

Реализовано по `SPEC_signage_bot.md`. Два языка (RU/KZ), язык ответа = язык обращения.

## Архитектура потока (раздел 4 ТЗ)

```
Входящее (личный чат с ботом)
├─ voice/audio/video_note → ответ №2, лог, СТОП
├─ photo/изображение      → Фото-поток → Drive + вкладка Photos + заглушка №20
│                            + эскалация в тему (само фото) → mode=human, СТОП
├─ mode=human             → бот молчит, релеит сообщение в тему оператора, СТОП
├─ интейк в процессе      → сбор адреса / товарного знака
└─ text → классификатор (call #1) → решение:
          • intent ∈ always_escalate / can_answer=false / confidence<THRESHOLD → эскалация
          • повтор одного вопроса ≥2 → эскалация
          • can_answer=true → адаптация (call #2) → ответ клиенту
          • needs_data → лёгкий интейк (адрес/фото/товарный знак)
```

Панель оператора — супергруппа с Темами (одна тема = один клиент). Подробно — в ТЗ, раздел 10.

## Структура

```
bot/
├─ main.py            # сборка зависимостей, long-polling
├─ config.py          # чтение .env
├─ handlers/
│  ├─ user.py         # сообщения предпринимателей (основной поток)
│  └─ operator.py     # панель: темы, /take /close /list /takeover, релей
├─ llm.py             # классификатор (call #1) + адаптация (call #2) + RU→KZ
├─ kb.py              # кэш базы знаний + авто-рефреш
├─ sheets.py          # Log / Escalations / Intake / Photos / Buildings / KB
├─ drive.py           # загрузка фото
├─ state.py           # SQLite: users, escalations, связка topic_id↔user_id
├─ escalation.py      # создание/переиспользование темы, карточка
├─ photos.py          # Фото-поток
├─ intake.py          # лёгкий сбор данных
├─ buildings.py       # хук поиска по адресу (на пилоте — заглушка)
├─ schedule.py        # рабочие часы
└─ services.py        # контейнер зависимостей
scripts/seed_kb.py    # заливка KB_seed.csv во вкладку KB
tests/test_offline.py # оффлайн-проверки логики (без сети/секретов)
KB_seed.csv           # сид базы знаний (id 1–21)
```

## Установка

```bash
pip install -r requirements.txt
cp .env.example .env        # заполнить ключи и ID (см. ниже)
```

## Что подключить (заполнить в .env)

| Переменная | Что это |
|---|---|
| `BOT_TOKEN` | токен бота от @BotFather |
| `OPERATOR_GROUP_ID` | супергруппа с включёнными **Темами**; бот — админ с правом «Управление темами» |
| `ANTHROPIC_API_KEY` | ключ Anthropic (модель `claude-haiku-4-5-20251001`) |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | путь к `service_account.json` |
| `SHEET_ID` | Google-таблица, расшарена на email сервисного аккаунта (редактор) |
| `GDRIVE_FOLDER_ID` | папка Drive, расшарена на сервисный аккаунт |

В Google Cloud у проекта сервисного аккаунта должны быть включены
**Google Sheets API** и **Google Drive API**.

> Рабочие часы (`WORK_*`) — это часы бота/панели, а НЕ часы приёма/выдачи
> эскизов Управления из базы знаний (id 4). Не путать.

## Заливка базы знаний

```bash
python -m scripts.seed_kb            # зальёт KB_seed.csv во вкладку KB
```
Дальше менеджеры ведут KB прямо в таблице; бот подхватывает правки
не реже чем раз в `KB_REFRESH_SECONDS` (по умолчанию 5 минут).

## Запуск

```bash
python -m bot.main
```
Long-polling — публичный URL не нужен. Деплой на любой воркер-хостинг.

## Тесты

```bash
python -m tests.test_offline
```
Проверяют чистую логику без сети: определение языка, парсинг JSON
классификатора, рабочие часы, фильтрацию интентов KB, нормализацию адреса
и SQLite-состояние.

## Границы пилота

Бот фото **не анализирует** — папка Drive и вкладка Photos копят датасет для
будущего vision-модуля (роадмап, раздел 20 ТЗ). KZ-переводы при
`KZ_AUTOTRANSLATE=true` — машинный черновик на выверку менеджерами.
